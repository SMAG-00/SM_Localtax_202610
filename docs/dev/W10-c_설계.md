# W10-c 공통 검수 큐·수집 파이프라인·법령 저장: 구현 기록 (개발 문서)

2단계 설계(`docs/dev/2단계_설계.md`) 1장 W10-c와 3·4·5장, PRD-02 REV-01~03·PIPE-01~09·AIOPS-06에 맞춘 구현 기록입니다. 설계와 다르면 설계가 맞고 이 문서를 고칩니다. (2026-10-25 작성)

지키는 선: 코드와 시험 자료에 실제 법령·세무 문장, 세율·기한 값은 없습니다. 시험 견본은 지어낸 값이고 `시험용` 표시가 있습니다. 법제처 기관코드(`LAW_API_OC`)는 아직 없으므로 수집기는 기관코드가 없거나 원천이 미확인이면 외부 요청을 한 번도 보내지 않습니다. 상속세 및 증여세법은 감시 목록에 넣을 수 없습니다. 기능 키 `pipelines`·`review_queue`는 꺼진 채 출하합니다.

## 11. 구현 기록

### 11.1 c1 (마이그레이션 86) - 원천 등록부·검수 큐·스냅샷 칸

| 항목 | 내용 |
|---|---|
| `data_sources` | 원천 키·종류·API 대상·우선순위, 이용 조건 `unchecked`(기본)·`allowed`·`link_only`·`denied`(확인자·시각 필수), 실응답 견본 계약 확인(확인자·시각 한 쌍). 씨앗 6행 모두 미확인. `data_source_runnable(key)` = 허용 AND 견본 확인, 서비스 계정만 실행 |
| `review_items` | 종류 8종(`law_change` `legal_doc` `link_error` `link_candidates` `amendment_stage` `field_data` `ai_draft` `pipeline_failure`), (종류, 키) 유일, 필수 체크 키는 종류로 DB가 정함(입력 무시), `parts`로 부분 승인, `attempts` 0~3, `status_changed_at`. 표 UPDATE는 서비스 계정에 열지 않고 소유자 직접 UPDATE도 트리거가 거부, 지우기 0 |
| 전이 함수 | `review_item_transition(id, to, actor, reason, checked, parts)` 하나. 허용 `drafted→in_review·rejected·failed`, `in_review→approved·rejected·failed`, `approved→published·failed`, `failed→retry`(실패 직전 상태로, 3회까지). 승인은 필수 체크 전부, 반려는 사유, 실패는 오류 요약 필요. `review_item_assign`은 열린 항목만 |
| `review_item_events` | 생성·전이·재시도·배정을 같은 거래로 남기는 추가만 표 |
| 72시간 | `review_items_stale(at)` - 열린 상태에서 머문 시간이 72시간을 넘으면 1건(71시간 59분은 0) |
| `raw_snapshots` 확장 | `source_key`·`external_id`·`run_id`·`http_status`. 수집기 행(`source_key` 있음)은 고치기·지우기 거부, (원천, 번호, 해시) 유일, 주소에 `OC=`·`serviceKey=` 등 인증키 모양이 있으면 새 행 거부(기존 행은 검사하지 않음) |

### 11.2 c4 (마이그레이션 87) - 법령 표

`laws`(감시 목록 씨앗 15행: 지방세 4법 × 법·시행령·시행규칙 12 + 계산기 연관 국세 법령 3, 이름만. 이름에 상속세·증여세가 들어가면 제약이 거부) · `law_versions`(공포번호 + 시행일자 하나에 1행, 스냅샷 필수, 추가만) · `law_articles`(개정판마다 새 행, 추가만) · `law_events`(first_seen·revision·body_only, 사건 키 유일이라 크론 재실행 중복 0, 추가만) · `law_watch_state`(감시 중·오류·정지, 실패는 여기에만 기록). W10-a의 `rules_audit.law_event_id`에 외래키를 이 파일 끝에서 연결했습니다. 공개 뷰는 만들지 않았습니다(W10-d 89번).

### 11.3 c5 (마이그레이션 88) - 해석 문서 칸

`legal_docs`에 `origin`(manual·pipeline)·`source_key`·`source_doc_id`·`decision_kind`를 더하고, 수집기 행은 원천·원천 문서 번호·스냅샷이 모두 있어야 합니다. (원천, 문서 번호) 유일. `legal_doc_aliases`(다른 원천 번호를 같은 문서에 대응, 추가만). 수집기 후보는 권리 미확인으로 시작해 기존 공개 읽기 정책에 걸리지 않고, 새 칸은 anon·authenticated에 열지 않았습니다. `doc_type` 값 목록은 늘리지 않았습니다(결정 #4).

### 11.4 c3 수집 코드 (`workflows/src/pipelines/`)

| 파일 | 내용 |
|---|---|
| `law/law-api.ts` | SM `agents/law-api.ts` 복사·수정(출처·해시는 `SOURCE.json`). 기관코드 주입, 요청 주소를 만드는 한 곳에서만 키 사용, 저장용 키 없는 주소 반환, 지수 백오프 3회(1초·2초), 4xx는 즉시 실패, 오류 글에서 키 가림 |
| `law/law-watch.ts` | `classifyChange`(SM 판정 그대로) + `LawStore` 인터페이스로 바꾼 감시. 첫 확인은 기준 개정판(검수 항목 0), 공포번호·시행일자 변경은 개정판 + 감지 기록 + `law_change` 검수 항목 1건, 해시만 바뀜은 기록만 |
| `law/articles.ts` | 응답 JSON에서 조문 옮기기. 모양이 다르면 `ok=false`로 알림(조용히 비우지 않음) |
| `docs/collector.ts` | 행정규칙·행안부 해석·조세심판 결정례 수집기. 필드 이름 표(`DOC_SPECS`)는 `[확인 필요]`, 새 문서만 저장, 일자 변경은 검수 항목 1건, 다른 원천과 같은 문서면 별칭, 실패 격리 |
| `credentials.ts` · `gate.ts` | 인증키 검사기·가림·공개 주소 변환 / 관문(기능 키 켜짐 + 기관코드 + 원천 수집 가능, 하나라도 틀리면 요청 0) |

웹 앱 쪽 `apps/web/lib/server/pipelines/`가 저장소를 구현합니다. 모든 쓰기는 멱등이고 순서는 스냅샷 → 개정판 → 조문 → 감지 기록 → 검수 항목 → 감시 상태라서 중간에 끊겨도 다음 실행이 이어 채웁니다. 작업 `pipeline-law`(UTC 16:00)·`pipeline-docs`(UTC 16:10)는 `/api/jobs/[job]`과 `vercel.json`에 줄만 더했고 결과는 수와 건너뜀 이유뿐입니다. 연속 3번 실패하면 같은 날 1건의 `pipeline_failure` 검수 항목이 생깁니다.

### 11.5 c2·c6 화면

`/admin/review`(권한 `review_item.decide`): 원문(스냅샷 앞부분 3,000자)과 후보를 나란히, 필수 체크를 모두 확인해야 [승인] 활성, 반려는 사유 필수, 부분 승인, 담당자 배정, 72시간 경고 칩과 첫 줄 알림. `/admin/pipelines`(권한 `pipeline.manage`, 관리자만): 원천별 이용 조건·견본 계약 기록, 수집 가능 표시, 최근 실행 10건, 감시 상태. API는 `/api/admin/review-items`·`/api/admin/data-sources`이고 모든 처리에 감사 로그가 남으며 허용 밖 시도는 거부 감사입니다. 메뉴 항목 `review`(편집 책임자·관리자)·`pipelines`(관리자)를 더하고 메뉴 시험 기대 목록에 반영했습니다.
