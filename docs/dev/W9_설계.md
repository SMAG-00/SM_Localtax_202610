# W9 기존 기사 이관 · 도메인 전환 — 준비 설계 (개발 문서)

PRD-01A 4.16 MIG-01~06과 PRD_최종 11.1 W9를 구현할 때 도구·DB·화면·시험이 같은 이름과 같은 규칙을 쓰기 위한 약속입니다.

**범위 (PO 결정 2026-10-25).** 지금은 **준비만** 합니다 — 이관 도구, 주소 연결 규칙, 리허설 스크립트, 계획. 이관 실행과 도메인 전환은 2~5단계 구축과 내부 보고·합격 뒤입니다. 지금 단계에서는 현 사이트(localtaxresearch.com)·DNS·계정을 바꾸지 않고, 원격 DB에도 아무것도 적용하지 않습니다(마이그레이션 77은 파일만). 시험 자료는 모두 지어낸 값이며 실제 기사 글을 저장소에 넣지 않습니다.

| 칸 | 필수 | 뜻 |
|---|---|---|

| `title` | 예 | 제목 |

| `category` 또는 `category_code` | 예 | 분류 코드(S1N1…) 또는 이름. 4대 분야에 대응되지 않으면 오류(미배정 0) |

## 3. 주소 (MIG-02)

- 정규형: 호스트·`www`/apex·http/https·`view_type`·쪽 번호를 떼고 `/news/articleView.html?idxno=N`(N은 앞 0 없는 정수), `/news/articleList.html?sc_section_code=S1Nx`, 그 밖은 경로만. 규칙은 `scripts/migration/normalize.mjs`와 `apps/web/lib/site/legacy-redirect.ts` 두 곳에 있고 같은 표로 시험합니다.
- 표 `redirects`(마이그레이션 `20261025000077_w9_redirects.sql`, PRD 이름 그대로): `old_path`(유일)·`new_path`·`status`(301·308·404·410)·`reason`·`origin`(legacy_site·v12_deploy). DB가 막는 것: 301/308은 새 주소 필수, 404/410은 사유 필수·새 주소 없음, 제자리 이동 0, 옛 기사 주소의 새 홈(`/`) 이동 0, **연쇄 0(양방향 트리거)**. RLS 기본 거부, service_role만 읽고 씁니다. 행은 0 — 전환 때 `redirects.sql`(on conflict upsert, 여러 번 실행 가능)로 채웁니다.
- 목록 주소: 분류별로 같은 주제의 새 목록(위 2.3 `listPath`), 분류 없는 목록은 `/news`. 홈 일괄 이동 없음.
- proxy: `apps/web/proxy.ts`가 `/news/articleView.html`·`/news/articleList.html`만 먼저 보고, 기능 키 **`legacy_redirects`**(`settings.feature_flags`, **기본 꺼짐**)가 켜졌을 때만 `redirects`를 한 건 찾아 301/308(쿼리 안 붙임)·410을 돌려줍니다. 꺼져 있거나 표에 없으면 지금 동작 그대로입니다. 읽기 실패는 503. 도착 주소가 `/`로 시작하지 않거나 `//`이면 따르지 않습니다(열린 이동 방지). 켜기는 전환 당일 `feature_flags`에 `legacy_redirects: true` 한 칸(관리 화면 목록에 올리려면 W2-b 2.3 표와 `FEATURE_KEYS`를 함께 고쳐야 해서 지금은 하지 않음).
- v1.2 `/region/…` → `/local/…`: 배포 기록이 없으므로 매핑 행 0(W4 설계 결정 18). 기록이 확인되면 `origin='v12_deploy'` 행으로 같은 표에 더합니다.
- 검사 항목: 미결정 0 · 연쇄 0 · 중복 0 · 옛 기사→홈 0 · 404/410 사유. 정적 쪽 5곳은 새 주소가 정해질 때까지 **미결정**으로 보고서의 "전환 전에 정해야 할 주소"에 남깁니다.

## 4. 어댑터 · PO가 줄 것

### 4.1 지금 있는 것 (`scripts/migration/`)

`format.mjs`(형식·분류 대응) · `normalize.mjs`(옛 주소 정규형) · `validate.mjs` · `transform.mjs` · `urlmap.mjs`(매핑·검사·SQL) · `run.mjs`(dry-run·보고서) · `cli.mjs`(`adapt`·`dry-run`·`rehearse`) · `adapters/ndsoft.mjs`(저장한 기사 HTML·사이트맵·RSS 읽기) · `adapters/wxr.mjs`(워드프레스 내보내기). 네트워크·DB를 쓰지 않습니다. 같은 입력이면 산출물이 글자까지 같아 리허설 비교가 가능합니다.

### 4.2 자료를 받은 뒤에 할 일

DB 덤프(MySQL 등)를 받으면 덤프 칸 → 중간 형식 어댑터를 더하고(칸 이름은 덤프로 확인), 분류·필자·이미지 파일 매핑과 `articles` 적재기를 씁니다. 사이트 자체를 읽어 오는 것은 PO가 허락한 범위에서만(robots.txt·crawl-delay 준수)이며, 기본 방침은 덤프입니다.

### 4.3 전환 때 PO가 줘야 하는 것

1. **내보내기 자료**: 현 CMS의 DB 덤프 또는 관리자 내보내기(기사 전체 — 제목·본문 HTML·분류·필자·입력/수정 시각·상태·조회수 선택) + 사진·첨부 파일 묶음 + 필자 표. 불가하면 관리자 계정(읽기 전용)으로 목록 내보내기 허락.
2. **운영사 확인**: 현 사이트 운영사(엔디소프트 계약 여부)·덤프 제공 가능 여부·계약 종료일·서버 유지 가능 기간.
3. **도메인/DNS 접근**: 도메인 등록기관·DNS 관리 계정(TTL을 낮출 권한), `www`/apex 설정, Vercel 도메인 연결 권한, Search Console·네이버 서치어드바이저 소유 확인.

## 5. 전환 점검표 (당일 순서)

1. 기존 사이트 쓰기 중지 시각 기록 → 델타 기사 수집(MIG-04) → 델타 적재.
2. 원본 기사 수 = 이관 수 + 제외 수, 제외 사유 전부 기록. 표본 200건 7항목 최종 불일치 0.
3. `redirects.sql` 적재 → 매핑 검사 통과 → `legacy_redirects` 켜기 → 테스트 주소에서 301 표본 200건 + 주요 20곳 통과.
4. `--status published` 최종 실행 전에 이관 기사 `content_type=digest` 0, 권리 미확인 이미지 공개 렌더 0, `section` 빈 이관 기사 0 확인.
5. 사이트맵·canonical·공유 메타에 옛 URL 0, 링크 검사기 통과.
6. DNS 전환(TTL 사전 인하) → 소유 확인 → Search Console 주소 변경/사이트맵 제출 → 서치어드바이저 사이트 이전.
7. 기존 서버 유지(쓰기 중지) 확인, 롤백 책임자 대기.

## 6. 롤백

- DNS를 기존 사이트 값으로 되돌립니다(전환 전 레코드 값을 11장에 저장). 되돌릴 때 `legacy_redirects` 키를 끕니다.
- 전환 뒤 새 사이트에 새로 올라온 글은 롤백 전에 내보내 보관합니다(양쪽 쓰기 분기 금지).
- 롤백 리허설 1회 성공이 전환의 조건입니다(MIG-06). 유지 기간·책임자는 전환 2주 전에 확정합니다.
