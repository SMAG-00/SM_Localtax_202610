## 2. 작업 방식 (지켜 온 것)

- 단계마다 순서는 같다.
  1. 서브에이전트 구현 (한 차례에 도구 호출 약 25번에서 멈춘다 — 15~20번째에 보고하게 하고, 멈추면 `git status`로 진행을 보고 남은 일만 짚어 이어 맡긴다)
  2. `git add` (서브에이전트가 같은 폴더에서 다음 단계를 고치는 중이면 고친 파일만 골라서)
  3. 빠른 검사: 타입·린트·`check-env`·웹 단위·`node --test "scripts/__tests__/*.test.mjs"` + 바뀐 부분 DB 시험·E2E. 권한·메뉴를 바꾸면 메뉴 정확 비교 E2E(admin-ui d·admin-settings-ui a·admin-situations)도. 전체 회귀는 CI에 맡긴다 (2026-10-20 PO "서둘러")
  4. **새 마이그레이션이 있으면 push 전에 원격 적용 승인** — 공통 경로(바닥글·설정 읽기·로그인)가 새 표를 읽으면 원격에 없을 때 테스트 주소가 깨진다(2026-10-20 실제로 목록이 '불러오지 못했습니다'가 됐다)
  5. 커밋(작성자 admin@sunmyung.kr) → push
  6. CI·배포 후 점검·테스트 주소(관리자 로그인 포함) 확인. CI는 처음 실패한 곳에서 멈추므로, 공통 부분을 바꾼 뒤에는 CI 뒤쪽 E2E를 로컬에서 미리 몰아 돌린다
  7. 메모리·이 문서 갱신
- 검사는 반드시 `git add` 뒤에 돈다. `check-env`는 git이 추적하는 파일만 본다.
- 두 작업이 같은 PC에서 동시에 웹 빌드를 하지 않는다. `apps/web/.next`가 겹친다.
- 보고 첫 줄에 진행 위치(📍)를 붙인다. 보고는 한국어로 쉽게 쓴다.
- 통합 시험은 vitest로 돈다(`pnpm --filter @ltr/web test:integration`). `node --test`로는 돌지 않는다.
- 검색 속도 측정은 CI 밖에서 따로 돈다: `pnpm test:search-perf`.

## 5. 기술 메모

- `apps/web/lib/server/public/cache-policy.ts`는 Next 16.3 내부 동작(태그 만료 벽시계 대 단조 시계)에 기댄다.
  - Next를 올리면 `w2c-acceptance`가 다시 확인한다.
- `proxy.ts`는 공개 상세 화면마다 DB 확인 요청을 한 번 더 보낸다. 410·503 응답 때문이다.
  - 방문이 많아지면 줄일 후보다.
- `/admin` 미리 받기는 머리글 로고 링크에서 껐다. 메뉴 줄은 보통 링크다.
