# W12-e 평가·게이트 기반 (e1~e3): 구현 기록 (개발 문서)

4단계 설계(`docs/dev/4단계_설계.md`) 1장 W12-e, 2.1 번호 163~164, 3장 e 행, 4.2 평가셋에 맞춘 구현 기록입니다. 설계와 다르면 설계가 맞고 이 문서를 고칩니다. (2026-10-27 작성) e4(실행기·자동 회귀)·e5(165 품질 콘솔·경보)·e6(수용)은 W12-b·c·d 뒤에 만듭니다.

지키는 선: 이 단위의 코드와 시험 자료에는 실제 법령·세무 문장, 세율·공제·기한·한도 값, 정답 결론을 쓰지 않습니다. 기본 300문항과 확장 평가셋의 문항·정답·필수 근거·금지 주장은 PO가 쓰고 보조 세무 전문가가 교차 확인하며, 이 단위는 표·가져오기 화면·채점·게이트만 만듭니다. 시험 자료는 전부 `[시험용]` 표시를 붙입니다. 기능 키는 모두 꺼 둔 채 출하하고, 국세 금액은 만들지 않습니다. AI 경계 목록에 걸리는 폴더(`lib/agent`)는 건드리지 않았고 평가 코드는 `lib/eval`·`lib/server/eval`에 둡니다.

## 2. 정한 점과 확인 필요

| # | 결정 | 이유 |
|---|---|---|
| 1 | 마이그레이션은 163·164만 썼고 165(품질 콘솔·경보)는 e5 몫으로 남깁니다 | 설계 1장 e5 |
| 2 | 게이트 통과는 미응답·미채점·미확정이 0일 때만입니다. 미확정은 집계에서 빼고 따로 세되 통과를 막습니다 | 전체 정답률에 가려진 빈칸 방지 |
| 3 | 두 채점이 "같다"는 판정·치명 오류 유형·뒷받침 인용 수·역질문 누락·지어낸 답·감면 단정이 모두 같은 경우입니다 | 지표 입력이 모두 사람 판정에서 오므로 |
| 4 | 단계 리포트는 `base` 평가셋, 범위 리포트는 같은 범위 평가셋의 끝난 실행만 받고, 실제 API 재실행(`live_api`, 같은 fingerprint)이 통과해야 확정됩니다 | 4단계 설계 4.2 (게이트 판정 때 실제 API로 한 번 더) |
| 5 | 승인 함수는 올리기·켜기에서 `p_fingerprint`가 필수입니다(없으면 `fingerprint_required`, 리포트의 fingerprint와 다르면 `report_stale`로 거부하고 둘 다 감사 1행). 내리기·끄기는 지문 없이 가능합니다. W12-d·e4가 현재 조건의 fingerprint를 넘기면 EVAL-03(변경 시 재평가)이 승인 경로에 걸립니다 | 낡은 리포트로 승인 방지 |
| 6 | 4c 공개의 법률 조건(COMPLY 문서, 설계 5장 #9)은 아직 승인 함수에 없습니다. W12-d가 후속 마이그레이션(167 예비)에서 더합니다 | d6 몫 |
| 7 | 범위 플래그를 켜는 데 공개 단계 조건은 걸지 않았습니다 | PRD가 순서를 못 박지 않음 [확인 필요: PO] |
| 8 | 가짜 모델로 만든 답변은 실행 출처가 `fake`라 리포트에 쓸 수 있어도 실제 API 재실행이 없으면 확정되지 않습니다 | 시연 경로와 운영 승인 분리 |
| 9 | 월간지·총람 출처 문항은 평가 사용 권리(T1) 확인 표시 전 저장 0입니다 | 설계 5장 #4 |
