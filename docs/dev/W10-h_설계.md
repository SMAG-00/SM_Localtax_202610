# W10-h 분야 데이터 연동: 구현 기록 (개발 문서)

2단계 설계(`docs/dev/2단계_설계.md`) 1장 W10-h와 3·5장, PRD-02 4.13(PR-06·LG-15·DF-06·DF-07)에 맞춘 구현 기록입니다. 설계와 다르면 설계가 맞고 이 문서를 고칩니다. (2026-10-25 작성)

지키는 선: 코드와 시험 자료에 실제 법령·세무 문장, 세율·기한 값, 이용 조건·공공누리 문구는 없습니다. 시험 자료는 모두 `시험용` 표시가 있는 지어낸 값이고, 실제 원천 주소와 응답 필드 이름은 빈 자리(`[확인 필요]`)입니다. 원천 이용 조건(`data_sources.terms_status`)이 `allowed`이고 견본 계약 확인이 있기 전에는 외부 요청을 한 번도 보내지 않습니다. 기능 키 `field_data`는 꺼진 채 출하합니다. 마이그레이션 번호는 100~102만 씁니다.

## 1. 흐름과 단계

원천 → (관문) 수집 → 원본 스냅샷 → 후보 → 검수 큐(`review_items`, 종류 `field_data`) → 사람 승인 → 공개 반영(원천 ID 멱등) → 공개 뷰.

| 단계 | 내용 | 마이그레이션·코드 |
|---|---|---|
| h1 | 원천 어댑터 틀. 관문 3개(기능 키 `field_data` 켜짐 · 인증키 있음 · 원천 `data_source_runnable`)와 주소 칸이 모두 맞을 때만 요청. 목록 → 후보 변환(허용 칸 목록만 옮김, 가격류 칸은 옮기지 않음) → 값 해시 → 스냅샷 + 후보 | `workflows/src/field-data/*`, 웹 `lib/server/field-data/*`, 작업 `pipeline-field-data` |

## 3. 결정과 기본값 (PO 위임, 권고안 적용)

| # | 결정 | 이유 |
|---|---|---|
| 1 | 후보는 `review_items`(종류 `field_data`)에만 쌓고 `payload`는 고정 모양(`target`·`source_item_id`·`value_hash`·`kogl_type`·`changed_fields`·`fields`)이며, 허용 칸 밖의 키는 승인 거부 | 가격류 칸이 후보에 실려 오는 길을 구조로 막음 (스키마 검사) |
| 2 | 후보 검수 키는 `field:{원천}:{항목}:{값 해시 앞 16}:{유형 또는 none}`. 같은 값 재수집은 중복 거부로 후보 1건, 값이 바뀌면 새 후보 | 원천 ID 멱등 + 바뀐 값은 새 후보 (PRD) |
| 3 | 공개 반영은 DB 함수 `field_publish()` 하나. 승인 상태·원천 허용·공공누리 유형·제4유형 통과 기록을 다시 확인한 뒤 같은 거래에서 `published`로 바꿈 | W10-c 결정 7(승인은 상태만, 반영은 처리 단위). 공개 경로를 한 곳에 둠 |
| 4 | 단계 기록은 추가만이므로 원천 값이 바뀐 승인 후보는 `correction` 기록으로, 분양·행사는 갱신으로 반영 | 1단계 `project_events` 규칙 |
| 5 | 프로젝트와 원천 항목의 연결은 `project_source_links`(편집자 입력)를 따름. 연결 없는 항목은 후보를 만들지 않고 `unmatched`로 셈 | 프로젝트 번호를 어댑터가 지어내지 않음 |
| 6 | 제4유형만 전재 제한(PRD). `unmarked`(표시 없음)는 기록된 유형으로 보고 공개 가능. 본문 글자가 있는 대상은 지표 정의·사례 결과·쟁점뿐이고 나머지 대상은 구조화 칸만 공개 | PRD가 제1~4유형·표시 없음 5값을 기록하고 제4유형만 제한 |
| 7 | 제4유형 유사도 검사는 `settings.similarity_internal` 기준값을 그대로 씀. 통과 기록(`field_candidate_checks`)에는 DB가 계산한 본문 해시를 적고, 공개 때 같은 해시가 있어야 함 | 기준값은 설정 (PRD). 검사 뒤 글자를 바꿔 우회 불가 |
| 8 | 금융 사례 DB는 새 표 `finance_case_entries`. 1단계 `finance_cases`는 기사 번호가 기본 키라 그대로 둠 | PRD 모델(`article_ids[]`)과 1단계 구조 충돌. 기존 표·가드 변경 0 |
| 9 | 승인된 금융 사례 후보는 `draft` 항목으로 들어가고, 반론 기록 등을 채운 뒤 공개 전환(가드가 막음) | 후보 내용은 고정이라 반론 기록을 승인 시점에 알 수 없음 |
| 10 | 새 변수 `DATA_API_KEY`(공공데이터 인증키)·`DATA_API_DART_KEY`(DART). 값은 비워 둠. 요청 주소는 키를 넣어 만들고 저장 주소는 키 모양 칸을 지움 | PO 준비물 #4 |
| 11 | 작업 `pipeline-field-data`(UTC 16:30, 하루 1회 줄)가 수집과 승인된 항목 공개 반영 대기분 처리를 함. 제4유형인데 통과 기록이 없으면 검사를 먼저 돌리고, 차단되면 승인 상태로 둔 채 수만 보고 | 상태 전이 남발 방지 |

## 4. PO 준비물 (2단계 설계 5.1)

#4 원천별 이용 조건 실사 결과를 `/admin/pipelines`에 기록(허용이면 근거 필수) · 실응답 견본으로 각 원천 어댑터의 주소·필드 이름 칸(`FIELD_SPECS`)을 채움 · 견본 계약 확인 기록 · `DATA_API_*` 키 신청 · 기능 키 `field_data`와 해당 분야 기능 키 켜기(원천 조건이 갖춰진 뒤) · 행사 이미지 권리를 원천별로 확인.
