# 「김의효 지방세연구」 PRD-X — 후속 선택 과제: 명소·맛집·TourAPI·지도 (1단계 범위 아님)

PRD_최종 v1.6(2026-10-16)은 지역명소·축제·맛집·관광 정보가 **지방세 전문지의 권위를 손상**할 수 있다는 PO 결정에 따라 지역 허브를 전문 뉴스 허브로 좁혔습니다. v2.1 정리본(2026-10-16)은 그 판단을 유지하되 **행사안내를 뉴스가 아닌 정보 목록으로 1단계 지자체 허브 안에 다시 열었습니다** — 세무·재정·개발 행사 우선, 축제는 지자체 허브 안에서만, 필수 필드·공식 URL·상태·확인일, 상업 행사는 `sponsored`, `Event` 구조화 데이터(PRD_최종 §5.4 LG-09~14·16, PRD-01B). 그래서 관광 제외는 이제 **명소·맛집·TourAPI·지도**에만 남습니다. 이 문서는 그 기능을 **삭제하지 않고** 후속 선택 과제 후보로 보존합니다. 지도는 지자체 허브의 이후 기능(P2, PRD_최종 §4.2)이고, 축제·행사 표준데이터 연동은 2단계 LG-15(PRD-02)입니다. 이 문서의 요구사항은 모두 P2입니다. 별도 수요·편집 인력·수익·브랜드 영향을 검증해 채택을 결정하기 전에는 어느 단계의 스키마·API·메뉴·발행 범위에도 넣지 않습니다. 일반 관광 콘텐츠가 별도 독자·편집 인력·수익 가능성을 입증하면 독립 브랜드/사이트를 먼저 검토합니다.

## 1. 목적과 범위

### 1.1 왜 분리했나

- PRD_최종 v1.5까지는 지역 허브의 명소·축제·맛집·생활정보를 1단계 P0으로 공개하려 했습니다. PO(세무사)는 2026-10-16에 지역명소·관광이 **지방세 전문지의 권위를 손상**할 수 있다고 판단해 v1.6으로 고쳤습니다.
- v2.1(2026-10-16)은 행사안내를 정보 목록으로 1단계에 다시 열었습니다 — 세무·재정·개발 행사(주민설명회 등) 우선, 축제는 지자체 허브 안에서만 (PRD_최종 §5.4). 그래서 축제·행사 달력·회차·상태·확인일·만료 규칙(REG-04·REG1-04·REG1-05)은 PRD-01B로 옮겼고, 이 문서에는 명소·맛집·TourAPI·지도만 남습니다.
- PRD_최종 v1.7 §0.5의 판단 — 전국 관광·맛집/축제 포털과 지방세 전문지를 한 메인 메뉴에서 동등하게 운영하는 안은 1단계 비권고입니다. 취재 인력·권리 관리가 분산되고 방문자가 매체의 주된 전문 분야를 이해하기 어렵습니다. 원본 기능은 삭제하지 않고 후속 후보로 보존합니다.
- 1단계에서 지역은 취재 대상과 독자 탐색 축입니다(§0.4). 축제·명소·상권 소재는 예산/세수/공유재산/개발/거래/주거 영향의 검증 가능한 관계가 있을 때만 전문 기사로 다룹니다(PRD-01B REG1-17). 여행 후기·맛집 추천·상업 행사 홍보 원고(행사안내의 상업 행사는 `sponsored`, PRD-01B LG)는 1단계에서 보류되거나 **별도 상품 검토 큐**로 가고, 그 큐가 이 문서의 수요 근거 중 하나가 됩니다.
- 지우지 않고 보존하는 이유 — 원본 PRD-04의 권리·동기화·날짜 처리 조건과 v1.0의 수용 기준은 다시 만들기 어렵습니다. 일반 관광 콘텐츠가 별도 독자·인력·수익을 입증하면 독립 상품에서 그대로 쓸 수 있습니다.

### 1.2 채택 판단 기준

**범위 판정 질문** (PRD_최종 v1.7 §0.5): (1) 지방세·부동산 세금·지방재정·도시/주택 정책 중 어떤 독자 문제를 설명하는가, (2) 관련성을 확인할 공식 자료/수치와 독립 취재가 있는가, (3) 기자·세무 감수 역량으로 지속 발행/정정할 수 있는가. 세 질문에 답하는 소재는 이 문서가 아니라 1단계 전문 기사(PRD-01B REG1-17)로 다룹니다. 이 문서의 후보는 어느 하나도 답하지 못하는 일반 관광·맛집·명소 정보입니다. 행사는 1단계 행사안내 정보 목록(PRD-01B LG-09~14·16)의 기준을 따릅니다.

**채택 안건을 올리기 전에 모두 갖출 증거**

| 증거 | 무엇을 보는가 | 출처 |
|---|---|---|
| 별도 독자 수요 | 1단계 별도 상품 검토 큐의 원고 수·주제, 관광성 검색어(예: `○○ 축제`)의 지역 검색 유입, 기존 사이트 관광성 URL 실사(6장)의 유입 | PRD-01B REG1-17 · REG1-15 · MIG-02 |
| 편집 인력 | 행사 일정 재확인·사진 권리·음식점 정보 확인을 맡을 인력과 비용. 전문 보도 인력을 빼 오지 않습니다 | 채택 검토 때 [결정 안건] |
| 수익 가능성 | 광고/제휴·지역 사업 수요와 상품별 공헌이익 가설(유료 매출 − 직접/변동 비용) | PRD_최종 v1.7 §0.4 |
| 브랜드 영향 | 독자 대상 `이 매체는 무엇을 전문적으로 다루는가` 응답, 전문 독자 재방문, 기사 → 문제해결 이동 | PRD_최종 v1.7 §0.5 · PRD-01A 12장 |
| 권리·계약 | TourAPI 운영 계정 계약, 지도 사업자 약관, 음식점 사진·후기·메뉴 권리 | 4장 · PRD_최종 v1.7 §7.2 |

**독립 브랜드 검토:** 일반 관광 콘텐츠가 별도 독자·편집 인력·수익 가능성을 입증하면 **독립 브랜드/사이트**를 먼저 검토합니다. 도메인 분리만으로 검색 품질이나 뉴스 제휴가 보장된다고 주장하지 않습니다(§0.5). 같은 사이트에 둘지는 7장 결정 안건입니다. 같은 사이트에 두더라도 콘텐츠 유형은 `지역 장소/행사 데이터`로 기사와 구분하고(PRD_최종 v1.7 §7.2.1 NAV-02), 관광 항목을 `reported_news`·자체 취재 집계·뉴스 전송 후보에 넣지 않습니다.

**결정 절차:** 채택은 PO 결정 기록으로 남기고 채택 범위의 요구사항 ID·단계 배치·영향 받는 테스트를 변경 기록에 적습니다(PRD_최종 v1.7 §0). 채택된 ID만 해당 단계 PRD로 옮기고 우선을 다시 정합니다. 채택하지 않은 ID는 이 문서에 P2로 남습니다.

### 1.3 채택 전 금지

- 1단계 스키마·마이그레이션에 3장 테이블을 만들지 않습니다 — "신규 저장소의 1단계에는 관광성 테이블을 미리 생성하지 않는다" (PRD_최종 v1.7 §6.1).
- 관광성 `items` API(`GET /api/regions/{code}/items`·`GET /api/regional-items/{id}` — kind place·food·life)와 지역 관광 동기화 작업(`POST /api/jobs/region-sync`)을 배포하지 않습니다 (PRD_최종 v1.7 §6.2). 행사 목록 API는 1단계 행사안내(PRD-01B)의 것입니다.
- 메뉴·홈·지자체 허브·사이트맵에 명소·맛집 카드·목록·지도를 두지 않습니다 (PRD_최종 v1.7 §3.1·§4.1 REG1-02). 축제는 1단계 행사안내 정보 목록 안에서만 다룹니다 (PRD-01B). `/local/.../places/[slug]`·`food/[slug]`는 새로 만들지 않습니다 — 예외는 6장의 기존 URL 보존. 행사 상세는 1단계 `/local/events/[slug]`입니다.
- TourAPI 키·지도 키·음식점 데이터 계약을 1단계 출시 의사결정에 넣지 않습니다 (§9). 신청은 채택을 결정한 뒤에 합니다 (인프라 요청서 11장).
- 1단계 뉴스 발행을 TourAPI에 의존시키지 않습니다 (§4.1 REG1-08).
- 시험 — 1단계 저장소의 마이그레이션·라우트 목록에 3장 테이블 이름이나 위 API 경로가 있으면 CI 실패 (1단계 PRD-01A의 같은 CI 검사).

### 1.4 이 문서의 벤치마킹 반영

해당 없음. 이 문서의 요구사항 근거 칸에는 BM-/RP- ID가 없습니다 (REG-02·REG-03·REG-05·AIOPS-13은 원본부터 `—`, REG1은 `PRD_최종 v1.7 §4.1` — v1.7 절).

### 1.6 상세본 대조 메모

- 상세본 v2.0이 없습니다(PO 확인). v2.1에는 이 문서의 ID가 직접 나오지 않고(§2.3 'v1.7 ID 유지'), 관광 제외의 범위만 바뀌었습니다(행사안내 재개방). 그래서 새 행을 만들지 않고 행사 관련 3개 행(REG-04·REG1-04·REG1-05)만 PRD-01B로 보냈습니다. 남은 8개의 수용 기준은 원본 그대로이며, 행사 데이터를 가리키는 원본 조건은 2장 머리 규칙으로 1단계 `events`에 맞춰 읽습니다.
- 근거 칸의 `PRD_최종 §4.1`(REG1 행)은 v1.7 절 번호입니다(원본 근거 유지). 본문의 v1.6·v1.7 참조는 `PRD_최종 v1.7 §x`로, v2.1 참조는 `PRD_최종 §x`로 적습니다.

## 2. 후보 요구사항

아래 8개는 모두 **P2 후속 선택 과제**입니다. 요구사항 칸은 앞에 PRD_최종 v1.6의 후속 선택 과제 문장을, 뒤에 v1.0 원본 행(PRD-01 4.15·4.16, PRD-02 4.13)의 문장을 '채택 시 원본 조건'으로 둡니다. 근거·수용 기준은 원본 그대로이며 **채택할 때** 적용합니다 — 원본의 '1단계'·'2단계'·'시범 지역'은 채택된 단계와 공개 지역으로 읽습니다. 원본끼리 가리키는 REG·REG1 행 중 REG-02·03·05·REG1-03·06·08·16·AIOPS-13은 이 문서 안의 행이고, REG-04·REG1-04·05·09·10·12·13·14는 PRD-01B, UX-01·NAV-04는 PRD-01A의 행입니다. 행끼리 수용 기준이 다르면 더 엄격한 쪽을 따릅니다. 날짜 판정은 한국 표준시(KST)로 합니다.

**행사 데이터 읽기 규칙 (v2.0)** — 원본 조건의 축제·행사 회차·상태·확인일·만료(`festival_occurrences`, REG1-04·05)는 v2.1에서 1단계 행사안내(`local_events`·`event_status_history`, PRD-01B LG-09~14·16, PRD_최종 §9.3)로 옮겨 갔고, 축제·행사 표준데이터 연동은 2단계 LG-15(PRD-02)입니다. 채택하면 TourAPI의 축제공연행사도 그 표와 규칙에 넣고, 원본 이름의 표를 새로 만들거나 같은 행사를 두 번 저장하지 않습니다.

### 3.2 재사용 규칙

- 1단계 테이블을 그대로 씁니다 — 지역 코드는 `regions.code`, 원본 스냅샷은 `raw_snapshots`, 관계는 `regional_links`. 채택 전에는 `regional_links`의 목적지로 관광 항목 유형을 저장할 수 없습니다(PRD-01B). 채택하면 `place/food/life` 목적지 유형(행사는 1단계 `local_events`)과 `nearby` 관계를 더합니다.
- `tour_items`·`tour_images`·`tour_sync_runs`라는 원본 PRD-04 이름을 이미 구현한 코드가 있다면 후속 상품 검토 때 재사용/확장하고 위 `regional_*` 기능을 뷰/추가 테이블로 매핑합니다. **같은 데이터의 이중 저장은 만들지 않습니다** (PRD_최종 v1.7 §6.1).
- 새로 만들면 위 통합 모델을 기본으로 합니다. 행정구역·공급자 코드, 장소 중복, 행사 회차, 편집 설명/원본 분리는 마이그레이션 문서에 필수로 적습니다.
- 독립 브랜드/사이트로 가면(7장) 계정·DB·배포를 따로 둘지, 같은 DB의 별도 스키마로 둘지를 그때 정합니다 [결정 안건]. 어느 쪽이든 1단계 기사 테이블에 관광 항목을 섞지 않습니다.

| `GET /api/regions/{code}/items?kind=place` | 지역 항목 목록(장소·음식점·생활정보) | 비공개·권리 미확인 항목 0. 행사는 1단계 행사안내 API(PRD-01B) |
| `GET /api/regional-items/{id}` | 항목 상세 | 비공개·권리 미확인 항목은 404 |
| `POST /api/jobs/region-sync` | 동기화 실행 | 인증된 서버/관리자 경로만. 같은 작업을 명령줄로도 실행합니다 (REG1-08 · AIOPS-13) |

공개 응답은 승인·권리·시점 필터를 서버에서 강제하고 `source`·`verifiedAt`·`status`를 포함합니다. 페이지는 서버 렌더링을 기본으로 하고 검색 엔진에 필요한 본문을 클라이언트 전용 API 호출 뒤에만 나타나게 만들지 않습니다.

## 6. 기존 사이트의 관광성 URL 처리

이 장은 **PRD-X 채택 여부와 관계없이** 운영 도메인 전환(PRD-01A MIG — 운영 도메인 전환) 때 적용합니다. PRD_최종 v1.7 §3.1·§6.1 — 기존 유효 URL이 있으면 삭제하지 않고 이관·권리/색인 실사를 하고, 삭제나 일괄 `noindex` 전에 유입·권리·품질을 실사해 URL별로 보존/이관을 결정합니다. 1:1 매핑·301·404/410 사유 기록은 PRD-01A MIG-01·MIG-02를 그대로 따릅니다.

| 순서 | 할 일 | 증거 |
|---|---|---|
| 1 현황 | PRD-01A MIG-01 현황 목록에서 관광성 URL(장소·축제·행사·음식점·여행 소개 등)을 표시합니다 | 현황 목록의 `관광성` 표시 열 |
| 2 실사 | URL마다 최근 검색 유입·외부 링크, 사진·글 권리, 정보 신선도(행사 일정·영업 정보), 내용 품질을 기록합니다 | URL별 실사 기록 |
| 3 결정 | `보존`(재분류 — REG1-17 관계가 있는 기사는 전문 기사 분야로) · `보존 페이지`(옛 게재 내용 그대로, 색인 여부는 품질로 판단) · `이관 보류`(PRD-X 채택 대기) · `제외`(404/410 + 사유) 중 하나 | `redirects` 행과 결정 기록 |
| 4 대응 | MIG-02 1:1 매핑표에 반영합니다. 관련 없는 홈 일괄 이동 0, 301 연쇄 0 | 링크 검사기 전수 결과 |
| 5 전환 후 | 2주 동안 매일 404·검색 콘솔에서 관광성 URL 오류를 봅니다 (PRD-01A MIG) | 점검 기록 |

- 보존 페이지에 남는 행사 일정·영업시간 같은 시간 민감 정보는 현재 정보처럼 보이지 않게 게재일을 표시합니다 [결정 안건: 표시 문구].
- `이관 보류` URL의 전환 시점 상태는 7장 결정 안건입니다 (기본 제안: 보존 페이지 + `noindex`).
- 시험 — 관광성 표시가 있는 옛 URL 중 실사 기록이 없는 행 0 (매핑표 확정 불가). `보존` 결정 URL은 301 한 번에 200 페이지. 실사 없이 404/410·`noindex`로 일괄 처리한 행 0.
